Design concept · for faculty review

Skill-String Curriculum Map

A course’s skills connect it to the courses before and after it. Catalog competencies collect those skills as evidence. Objectives and goals, set with Bloom’s taxonomy, say what a course aims for. Only a capture can show what it achieves.

Date 2026-11-16 Status Partly built Audience Faculty, curriculum committee
01

The idea in brief

The current curriculum map links courses through catalog competencies: a course raises Color management to a level, and a later course needs that level. This concept adds the step below, the skills a course actually develops and requires. A skill is written as the course writes it and is scored on Know, Understand and Do. A later course states the skills it needs on arrival, and the map shows which earlier skill meets each one.

Competencies keep their place with a different job. A competency is no longer the connector. It becomes a bucket of evidence: the skills linked to it, across all courses, are the record that students have had the chance to develop it, and to what level. Career targets and program targets still read competencies.

Two kinds of statement are kept apart throughout.

  • Goals say what a course aims for: its learning objectives, written with Bloom’s taxonomy, and the KUD goals that go with them.
  • Outcomes say what students actually do, and they come only from evidence: the course capture, with its assessed student work.

Mapping is a drafting process. While mapping, faculty can add objectives and KUD goals to a course and use them to check off later courses’ requirements. Every such draft is marked in the map (italic, with an asterisk*). It stays listed on the course as work to be confirmed through a capture before it counts as achieved.

All the skill-to-competency work done so far still applies: those links are the buckets.

What is built (November 2026)

Built. On the curriculum builder’s map, each required skill is linked to the earlier skills that supply it. A model on the campus servers rates each link fully or partly, with cut-offs set from faculty decisions, and faculty can confirm or change it. Each required skill shows Met, Met* (met only through a draft), Partly met or Not met (§8). Faculty can draft changes to a course on the map, and a draft that meets a requirement is listed to be confirmed through capture (§7). Strings can be locked into named, lasting connections across courses, and a locked string keeps its links when a course is captured again (§9).

Not built. Objectives as records with Bloom cells and KUD goals (§6), the competency fallback and the Proposed, Via competency and No data statuses (§4, §8), requirements split into parts, review by exception (§9) and the needed shape (§10).

Where strings sit: under prerequisite edges

The tool already has a prerequisite edge for each pair of courses: a later course, an earlier course, a competency, and the K/U/D levels the later course relies on (Background §12). The gap engine reads those edges, and so do what-ifs. Strings do not replace them. A string adds skill-level detail inside an edge: which of the earlier course’s skills supplies which of the later course’s required skills. The gap engine stays the judge at competency level, with its basis stamp (measured, mixed, intended, none) unchanged. Strings explain the result and can narrow it, but they never pass a requirement the edge fails.

Every link is a separate record that software proposes and faculty confirm or change. A captured skill’s wording and scores never change because of a link or a draft.

04

Skills as strings

The KUD Background sets the framework’s job as tracing “a competency from one course to the next, through an entire curriculum, and into a career destination” (§5). Tracing at the skill level keeps more of what each course says. A course that needs students to “set up a press-ready file with correct bleed and color handling” is asking for something narrower than “Color management at Do 3,” and the earlier skill that supplies it should be visible.

A string links a required skill to a developed skill

Each string records how fully the earlier skill covers the requirement, fully or partly, and whether faculty have confirmed it. A requirement is met by one string rated fully whose skill reaches the required level on every dimension the requirement names. A partly string is shown as a partial source and never meets a requirement on its own. When several fully-rated strings each meet the requirement, the best one counts. Levels are not added, because they are ordinal (Background §12).

Requirements that need several skills

“Prepare a press-ready file with correct color handling” needs both file preparation and color conversion. Such a requirement is split into parts, held together as an all of group. The group is met only when every part is met, and its weakest part decides its status. Splitting is proposed by software and confirmed by the instructor of the later course.

How strings are proposed

  1. Shortlist. The candidates are developed skills from earlier courses, inside an existing prerequisite edge or under the same competency as the requirement, plus the nearest skills by embedding.
  2. Judge. A model on the campus servers reads both skills and both courses’ context and answers whether the earlier skill covers the requirement fully, partly or not. This is the judge planned for skill-to-competency links. On public benchmarks, asking a model directly, with course context, matched more costly methods (2026-11-15 results note). Two cautions apply. Those benchmarks matched objectives or job sentences to skill catalogs, not one course’s skill to another’s, and setting cut-offs on faculty decisions is this design’s plan, not something the tests did. A one-course test comes first.
  3. Confirm by exception (§9).

Competencies as the fallback

A required skill with no string can still be read against its competency bucket. That needs a link from each required skill to a competency, which does not exist yet: required skills today have a wording and expected levels, but no competency. It is a fourth kind of link, proposed and confirmed like the others. It also tells the tool when a requirement belongs to a foundational competency, which is scored on Do only.

05

Competencies as evidence

A competency collects the skills linked to it across courses, and its level is read from them. That is how the builder has worked since the skill links went live on 2026-11-15. A skill counts toward a competency through a link that is proposed, confirmed or rejected. The competency’s level comes from the highest linked skill, unless faculty set it.

Treating a competency as a claim supported by evidence, rather than a thing a course covers, follows established assessment design. Evidence-centered design separates what is to be known about a student from the observations that support it: “A Student Model defines one or more variables related to the knowledge, skills, and abilities we wish to measure” (Mislevy, Almond & Lukas, 2004, p. 7). Its measurement models “concern the accumulation and synthesis of evidence across tasks, in terms of student model variables” (p. 10). Read onto this map, a competency plays the part of a student-model variable, the skills in many courses are the observations, and the roll-up is the accumulation. This is an analogy, not a claim that the map is a measurement model in their sense. Its levels are faculty-confirmed judgments of what courses give students the chance to develop, not estimates of what one student knows.

Only captured outcomes fill a bucket. Draft goals (§7) are shown beside a bucket, marked, and never raise its evidenced level. A competency with links only from courses not yet captured shows as claimed, as the prerequisite-gap method already does.

Mapping skills to assessments and reading skill development from assessment results has been done before. Jayalath et al. mapped each assessment “to one or more skills, with weights adding up to 100 per assessment” (Jayalath et al., 2026, PDF p. 4). They note that mapping is often done in a way that “merely records the presence or absence of skills embedded in assessments” (PDF p. 1).

06

Objectives and goals, set with Bloom

Learning objectives are written with the revised Bloom’s taxonomy. That is a department convention for how objectives are worded, and it fits what the KUD Background already says: Bloom is the right tool for a course’s objectives and assessments, and KUD is the tool for tracing across courses to careers (§5). Bloom here sets goals only. An objective’s Bloom wording never says that a level was reached. Reached levels come from the capture.

What Bloom gives an objective

In the revised taxonomy an objective has two parts. Objectives “consist of a noun or noun phrase—the subject matter content—and a verb or verb phrase—the cognitive process(es)”, and the revision separates them, “the noun providing the basis for the Knowledge dimension and the verb forming the basis for the Cognitive Process dimension” (Krathwohl, 2002, p. 213). The six processes run from “Remember – Retrieving relevant knowledge from long-term memory” to “Create – Putting elements together to form a novel, coherent whole or make an original product” (p. 215). An objective with two verbs belongs in two cells; Krathwohl’s example is placed in “two cells of the Taxonomy Table” (p. 216).

From an objective to KUD goals

Each objective carries one or more KUD goals: a skill, the dimension it aims at, and a target level. The Bloom wording proposes the dimension. The target level is set by the instructor, helped by the condition phrase in the objective. The table below proposes; the instructor decides. A further proposal, under review, would reword the Know and Understand levels themselves in Bloom’s 19 process names, with AND/OR rules per level; it is set out in the KUD Background, §5. If adopted, it would replace the level column of this table.

Two cautions built into the link

“Understand” means two things. Bloom’s Understand is “Determining the meaning of instructional messages” (Krathwohl, 2002, p. 215), a lower level than KUD’s Understand, which is reasoning about why. The interface always labels which one it means.

Bloom does not grade independence. Apply is “Carrying out or using a procedure in a given situation” (p. 215) whether or not the student needs direction. So a Do target needs a condition phrase or the instructor’s choice (Background §5). An Apply or Create objective with no condition is marked “condition missing” until a level is chosen.

The verb alone cannot settle the Bloom level either. Stanny compared 30 published verb lists: of 433 distinct verbs, “197 verbs (45.5%) appeared in two to six categories”, and “No verb was assigned consistently to the same category by all 30 lists in the sample” (Stanny, 2016, p. 4). Her conclusion is the rule this design follows: “reviewers must consider both the verb and the remaining content of an SLO when they make judgments about the level of expertise an SLO describes” (p. 10). The Bloom cell is proposed from the whole objective, verb and object together, and the instructor confirms it.

Faculty can agree well on Bloom levels. In a study of computing programs, two blind faculty raters assigned Bloom levels to a sample of competency statements and agreed at “Bloom level κ = 0.86” (Turaev et al., 2026, p. 1). Their few large disagreements came on multi-verb outcomes, where leveling by the leading verb “parts company with leveling by the highest-order verb” (p. 10). That was one field, and a Bloom level, not a KUD level. This design gives each verb its own cell, as in Krathwohl’s two-cell example, which avoids choosing between the two conventions; that is this design’s choice, not a tested result. Software proposals are useful but not reliable enough to stand alone. In one study of 600 labeled sentences from exam questions and learning outcomes, a trained classifier reached “94% accuracy, recall, and F1-scores”, while language models asked without examples reached “0.72–0.73 accuracy” at best (Kumar, Gulwani & Singh, 2025, PDF p. 1). That study used the original Bloom categories and a single dataset, which the authors name as a limit (“we work on a small-size and a single dataset”, PDF p. 6).

One link table, read both ways

There is one table of objective-to-skill links, read from either side. Read from the objective, it answers what in this course carries out this goal, and has a capture shown it? Read from the skill, it answers which goal does this work serve? Four results come out of it:

  • Goal reached. A captured skill linked to the objective reaches the goal’s target level.
  • Goal not yet reached. Linked captured skills exist, but below the target. This is the “objective misalignment” a capture’s audit notes already record, now tied to a specific skill.
  • Goal with no outcome. No captured skill is linked: the goal is still only a goal.
  • Outcome with no objective. Work the course does that its objectives do not state. The tool can draft a Bloom objective for it from the skill’s wording, using the fixed phrase table the syllabus requirement lines already use. A drafted objective is a goal written to match existing evidence; it is marked as drafted from an outcome and is never counted as an independent check of that outcome.

This is constructive alignment at the course level. Biggs asks that teaching and assessment line up with the intended “performances of understanding” (Biggs, 1996, p. 347), and backward design asks first “What should students know, understand, and be able to do?” (Wiggins & McTighe, 2005, p. 17). This replaces the objective proposal in Background §11 and keeps its gate: before the proposals are trusted, measure on the department’s own objectives how often they are right.

07

Drafting while mapping

While mapping, a faculty member can add to any course in the plan:

  • a draft objective, with its Bloom wording and KUD goals;
  • a draft KUD goal on its own: a new skill with a target level, or a higher target for an existing skill;
  • a draft required skill for a course that needs something on arrival.

Drafts can check off requirements in the map, so a committee can see whether a planned change would close a gap. They are never mistaken for evidence:

  • In the map, a draft is set in italic with an asterisk*. A requirement met only through a draft shows met*, never plain met. A draft level beside a captured one shows both: D2 captured · D3* goal.
  • On the course, a list headed To confirm through capture holds every draft added to it, with who added it and when. The list empties only through the course’s next capture: the capture either shows the draft happened, so it becomes a captured outcome, or shows it did not, so it stays a goal.
  • In competencies and targets, evidenced levels and draft levels are kept apart. An act target reads “met” on evidence or “met*” with drafts, never a blend of the two.

A capture never takes a draft as given. The capture interview is told what the instructor drafted, so it can ask about it, but the evidence rule decides the scores.

Requirement statuses

Every required skill of every course shows one status, taken from the first row of this table that applies. Statuses are computed for the plan or what-if being viewed.

StatusRule
MetA confirmed string rated fully, from a captured skill, reaches the required level on every dimension named.
Met*As above, but only by counting a draft goal (§7), whether a draft level, a draft skill or a draft string.
ProposedA string that would meet it exists but nobody has confirmed it. Drawn soft until someone confirms it.

Fade is shown separately. A met requirement whose source is several terms back with no reinforcement in between also shows may fade, using the builder’s per-term rule. It does not change the status. The prerequisite-gap method treats durability as outside the gap calculation (Background §12), and this keeps to that.

A string’s fully or partly rating decides whether it can meet a requirement; it never changes a level. Levels come only from skills.

09

Reviewing by exception

With about 470 captured skills and a similar number of requirements to come, confirming every proposed string would ask each instructor for dozens of decisions. Review works by exception instead:

  • Who reviews. The instructor of the later course owns its strings, since the requirement is theirs. The earlier course’s instructor sees every string that depends on their skills and can comment. Each decision is recorded with the person’s own login.
  • What is asked. Only what is uncertain or matters: proposed strings near the judge’s cut-off, partly-rated strings, requirements that are not met or met only via competency, and anything changed by a new capture. Confident proposals stay proposed; they are visible and never shown as met.
  • A budget. Each round asks an instructor for a fixed, small number of decisions, starting with the requirements that block the most.

Faculty decisions also tune the judge: they set its cut-offs (results note). Lê et al. show the shape of a tagger built for review, using “a large language model (LLM) as a constrained, evidence-producing tagger” (Lê et al., 2026, p. 1).

Decisions must survive a new capture

Today a skill is identified by its capture and a fingerprint of its wording. When a course is captured again, its skills get new identities, and links made on the old ones no longer apply. Strings join two courses, so a new capture of either one would lose them. Locked strings solve this: each linked skill is matched to the skill that continues it in the course’s latest capture, so faculty decisions carry over, and a reworded skill is shown for faculty to confirm. This also protects the skill-to-competency links already live.

10

From drafts to a what-if

Drafts live in a what-if, never on the course record. The what-if feature specified on 2026-11-13 already holds a changed version of one course and shows what follows across the program. Drafting adds the skill level to it. A faculty member opens a what-if from their course, adds draft goals or objectives, and watches later courses’ requirements change to met* or stay short.

The needed shape

Strings give each course a needed shape: a list, not one merged number. Each entry is a requirement in a later course that relies on this course, the level it needs, and whether another earlier course already meets it. Only entries that no other course meets are marked as this course’s to close. Competency targets per act are shown in a separate list, since they are a different kind of need.

Course B’s needed shape (from the §3 demo)

Rows that Course B supplies and are not met are Course B’s to close; a row another course already meets is shown but not counted. Later courses’ requirements are themselves claims that can be wrong. The needed shape shows who asked for each entry, so a gap can be settled by changing either course.

When the changed course is next captured, its To confirm through capture list is checked against the new capture. Comparing a what-if’s plan with the capture that follows is already planned for later what-if work.

11

A smaller first step

Most of the value can be tested before strings are stored:

  1. Link each required skill to a competency (the fourth link type), proposed and confirmed like the others.
  2. For each required skill, run the existing gap engine at competency level, and list the earlier skills under that competency as candidates, without storing strings.
  3. Let instructors pin a string only where the list is wrong or a requirement is short.
  4. Walk one real three-course chain on paper with its instructors before any build.

Drafting (§7) and the needed shape (§10) can follow on that base. Stored strings, review by exception and skill identity across captures come next, if the paper chain shows they are worth it.

13

Decisions still open

  1. Review budget. How many decisions per instructor per round is acceptable?
  2. Required skills for courses not yet captured. Draft them from catalog prerequisites and the syllabus as claimed, or leave them empty until captured?
  3. Foundational objectives. Objectives about agency, attention to detail or resilience fit Bloom poorly. Should they carry Do goals only, matching how foundational competencies are scored?
  4. Metacognitive objectives. The revised taxonomy’s fourth knowledge type, “Knowledge of cognition in general as well as awareness and knowledge of one’s own cognition” (Krathwohl, 2002, p. 214), may fit the problem-solving conditions (structured post-mortem, revision cycles) better than any one skill. Should these objectives link to conditions instead?
