Inside the GC Advisor

What happens when an advisor asks it a question, which models and data it relies on, and what breaks when one of those is down.

Code as of main 23d9708 · 25 Nov 2026 · pi 1.6.0

What it is

The advisor is a chat assistant for faculty and staff advising students. You ask things like “can she take GC 3400 next spring?” or “find her a section that fits around CRN 80822”, and it answers from the live class schedule, the catalog, and the department's own planning rules, plus a student's Degree Works audit if you paste one in.

It is one program on one department computer, reachable only from a campus web front door that requires sign-in. The language model doesn't know Clemson's rules itself. It decides which lookups to make, and the lookups (“tools”) return the facts. Several answers are worked out by code rather than by the model: degree checklists, schedule fits, and whether a plan works.

It covers eight College of Business programs. Graphic Communications BS is the only one whose degree-audit verdicts are treated as authoritative.

  1. Sign-in. Only faculty and staff who have been given access can sign in. The session lives only in the server's memory and ends after two idle hours.
  2. The question arrives. The page sends the message to the server. Only one question runs per session at a time, and closing the tab stops it.
  3. The prompt is assembled. A fresh set of instructions is built each time: the advisor persona, plus the chosen program, catalog year, the term being planned for, and any schedule or checklist already on screen. The earlier conversation is added after it.
  4. The model works in rounds. In each round the model either answers or asks for tools. The server runs the tools and hands back their results. A question may take up to 8 rounds, with up to 20 tool calls in one round, within 10 minutes.
  5. A second try when the first looks weak. Simple questions start with the model's step-by-step “thinking” switched off, for speed. If the first answer shows signs of trouble (repeated tool errors, results found but never displayed, or an advising question answered with no lookups), the question is rerun with thinking on.
  6. The answer comes back. While it works, the page shows progress (which tools are running). The full answer arrives at the end, along with updated schedule or checklist panels and a footer naming the model that answered.
  7. A shape-only record is kept. One line goes to the analytics log: question category, tool names, timings and the model used. The question and answer text are never stored.

The models

A dropdown on the page picks the model. Auto (the default at every sign-in) tries a chain of campus-hosted models in order and falls through to the next if one fails. Choosing a specific model uses that model alone, with no fallback, so failures show.

Research Computing and the OpenAI gateway share one Clemson key. A separate credential service adds it to requests as they leave, so the key is not stored in the advisor's own settings.

The software that runs the rounds is pi (pi-ai and pi-agent-core, an open-source agent library). It was upgraded from 0.82.1 to 1.6.0 on 25 November 2026.

The tools

Facts come from tools, and most tools live in two separate servers on the same machine. Those servers are a separate, public project (clemson-advising-mcp) that holds no student data and no credentials. The advisor connects to them with the standard Model Context Protocol (MCP).

Schedule server

Class sections from Banner: times, rooms, instructors, seats. A snapshot is refreshed at 5:00 and hourly 8:00–17:00; three tools read Banner live, for example seat counts.

Catalog server

Programs, requirements, gen-ed lists, course entries, prerequisites, and the department's own planning rules and approved course lists. Built yearly from catalog.clemson.edu.

Built-in tools

Code inside the advisor itself: show and save schedule options, build a verified schedule, read the degree checklist, record a substitution, check a graduation plan, load more tools, check system health.

Some answers are checked in code after the model writes them. When the advisor suggests a replacement class, the schedule server checks prerequisites against the student's completed and in-progress courses (taken from a pasted Degree Works audit when there is one). Courses the student can't take yet are left out. If an answer still names one without saying what's missing, a “Prerequisite check” note is added to the reply. A plan that fails the plan checker gets the same kind of note.

The model doesn't see every tool at once. A core set is always on; less common groups (extra curriculum lookups, scheduling extras, the GC wiki, help pages) are added when the model asks for them with load-tools. A server that is down is skipped, and the advisor retries it at most once a minute.

The servers limit how many requests each client can make. Benchmark runs share that allowance with the live advisor, so test runs are spaced out.

What people see

Chat

Program and catalog-year picker, model dropdown, “Planning for” term (Spring from 1 Oct to 15 Feb, Fall otherwise), optional voice input, export.

Schedule panel

One weekly grid with tabs for the current schedule, lettered saved options and numbered candidates. Paste a Banner schedule to check it. Hold a class to see alternatives.

Degree Works panel

Bring in an audit by bookmarklet, paste or PDF. It's cleaned in the browser, then turned into a checklist by code, not the model.

Degree Planner

A drag-and-drop semester plan built from the audit, coloured by prerequisites and how often courses are offered. Saved plans carry no names or C-numbers.

Admin tab

A separate chat for scheduling chairs, a section-planning workspace, enrollment forecasts with ranges, and course co-enrollment counts.

Feedback

A text box on the chat and planner pages. Notes are stored on this machine and deleted after 30 days.

Student data

The written policy in the repo (docs/policy/student-data.md) decides where identifiable student data may go. The rule is about destination, not content: since 19 November 2026 the page no longer screens what is typed.

  • Every model the advisor might call is checked against an allow-list in policy/action-policy.yaml at startup and again before each use.
  • Conversations live in memory only. Since the pi upgrade there is no transcript file on disk; clearing a chat or a restart discards it.
  • Nothing per-student is kept: analytics hold no text, planner saves are de-identified, and exported Degree Works PDFs are turned into anonymous checklists and deleted within 14 days.

How it's checked

  • Automated tests: 1,803 tests on the advisor and 451 on the benchmark tooling, all required to pass, with none skipped, before any merge.
  • Task benchmark: 31 scripted advising questions with known right answers (prerequisites, section fits, swaps, plan checks), run through the real advisor against the real models and tool servers.

Known gaps

  • The shared OpenAI credit pool can run dry without warning. It is shared across campus and has no balance check. The health check can tell when the Clemson key stops working, but not when the pool is empty. Benchmark runs against OpenAI need the department lead's approval and a spending cap.
  • Restarts end conversations. Sessions are in memory by design. pi now offers saved sessions, but that part is marked experimental.
  • Certificate renewal is manual. The campus certificate expires on 21 January 2027; the renewal request should go to IT in December.
  • Prerequisite checks use what Degree Works counted. Audits carry no grades, so a course counts as done only if Degree Works applied it somewhere. A passed course it didn't count anywhere is missed, and a course it unlocks is wrongly shown as not yet allowed.
