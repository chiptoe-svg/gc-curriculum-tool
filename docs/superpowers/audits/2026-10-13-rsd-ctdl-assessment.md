## 1. Open Skills Network (OSN) — Rich Skill Descriptors (RSD) and OSMT

### What it is / governance / activity

- RSD is "a detailed, machine-readable, standardized representation of skills," defined by a **working draft specification** maintained by OSN's Technical Workgroup. Source (`rsd-respec` GitHub repo, `README.md`, fetched via `raw.githubusercontent.com/roverwolf/rsd-respec/main/README.md`, 2026-10-13): *"Rich Skills Descriptor standards implementation recommendation documents are produced by the Technical Workgroup of the Open Skills Network to guide members and the public around options for working with skills data using interoperable open standards."*
- The spec's own abstract (`index.html` in the same repo): *"This document describes the Rich Skill Descriptor (RSD) class and how RSDs should be published for compatibility with services that process machine readable representations of skills and competencies. Each RSD is primarily identified by a canonical URL and consists of a skillStatement and supporting metadata to identify alignment to other skills or job categories."* It is explicit about its own status: *"This document is a working draft of a standards implementation recommendation document ... There is no conformance testing for implementers of these recommendations."* (same file, "sotd"/"conformance" sections). So RSD is guidance/convention, not a ratified, versioned standard with conformance testing — closer to a profile than to CASE or CTDL themselves.
- **RSD is explicitly built on top of CTDL-ASN, not a competing data model.** Spec text: *"RSDs build on CTDL-ASN to enable skill authors to publish definitions that can be referenced from digital credentials (including those that appear in learner records), pathways, and job profiles."* This is corroborated structurally by the RSD JSON-LD `@context` itself (`context-v1.json`, same repo, fetched 2026-10-13), which aliases every RSD term directly onto CTDL-ASN/CTDL terms:
  ```
  "Collection": "ceasn:CompetencyFramework",
  "RichSkillDescriptor": "ceasn:Competency",
  "skillStatement": {"@id": "ceasn:competencyText"},
  "skillName": {"@id": "ceasn:competencyLabel"},
  "category": {"@id": "ceasn:competencyCategory"},
  "alignments"/"standards": {"@id": "ceasn:majorAlignment", "@type": "@id"},
  "occupations": {"@id": "ceterms:occupationType"}
  ```
  i.e., an "RSD" **is** a `ceasn:Competency`, and an RSD "Collection" **is** a `ceasn:CompetencyFramework`. RSD is best understood as a friendlier vocabulary/authoring convention layered on CTDL-ASN, with an additional, alternate CASE-LD serialization recipe (see below) — not an independent third data model.
- Last real content commit to the spec repo itself: `pushed_at: 2021-07-16` (GitHub API, `repos/roverwolf/rsd-respec`, fetched 2026-10-13). The spec text carries a **copyright date of 2020** and has not had substantive updates since 2021. By contrast, the **OSMT tool repo is actively maintained**: now at `github.com/CredentialEngine/osmt` (the old `wgu-opensource/osmt` URL now redirects there), `pushed_at: 2026-07-27`, `updated_at: 2026-09-27`, not archived, with a merge commit titled "OSMT Update 2026" dated 2026-07-08 (GitHub API, fetched 2026-10-13). **This is a governance change worth flagging explicitly: OSMT's GitHub org of record has moved from `wgu-opensource` to `CredentialEngine`**, even though the tool's own marketing site `osmt.io` still displays WGU as operator (per its copyright/branding, WebFetch of `osmt.io`, 2026-10-13) and its last tagged *release* was `3.0.0` (2024-02-13) — commits continue past that tag without a newer version tag as of this check. **[UNVERIFIED]** whether this is a full governance transfer to Credential Engine, a shared-stewardship arrangement, or a GitHub-org housekeeping move; worth a direct question to Credential Engine/WGU if this ever becomes load-bearing.
- License: OSMT — Apache License 2.0, "Copyright 2021 Open Skills Network" (LICENSE file, `raw.githubusercontent.com/CredentialEngine/osmt/develop/LICENSE`, fetched 2026-10-13). RSD spec document itself — Creative Commons Attribution 4.0 (CC BY 4.0): *"This work is licensed under a Creative Commons Attribution 4.0 International License"* (rsd-respec `README.md`); the spec HTML repeats *"Copyright © 2020. This document is licensed under a Creative Commons Attribution 4.0 (CC-BY) License. Join the Open Skills Network to contribute."* (`index.html`).

### Data model

From the RSD spec's CTDL-ASN/CTDL property table (`index.html`, fetched via raw GitHub, 2026-10-13):

| RSD property | Maps to (CTDL-ASN/CTDL term) | Notes |
|---|---|---|
| `id` | `@id` | Canonical URL, "uniquely identifies the skill, from which more information may be retrieved" |
| `skillName` | `ceasn:competencyLabel` | Short label |
| `skillStatement` | `ceasn:competencyText` | Full statement |
| `category` | `ceasn:competencyCategory` | — |
| `keywords` | `ceterms:keyword` | — |
| `alignments` / `standards` | `ceasn:majorAlignment` (typed, `@type: @id`) | See alignment types below |
| `occupations` | `ceterms:occupationType` | "indicates skill alignment to relevant job roles/occupations aligned to an external categorization like BLS SOC or O*NET" (quote, `index.html` line ~215) |
| `certifications` | `ceasn:alignFrom` | External cert alignment |
| `containsSkill` (on a Collection) | `ceasn:hasTopChild` | Collection→member skill |

- **Alignment types** (verbatim, `index.html`): *"Available alignment types include majorAlignment, broadAlignment, exactAlignment, minorAlignment, narrowAlignment, and prerequisiteAlignment. The most simple or default recommendation is majorAlignment, which implies a close but not exact match."* These map directly to CTDL-ASN alignment properties (`ceasn:majorAlignment`, `ceasn:broadAlignment`, etc.) — so yes, typed broader/narrower/exact relations exist, inherited wholesale from CTDL-ASN.
- **Proficiency/depth levels: RSD/CTDL-ASN does *not* carry a depth or proficiency scale analogous to our 0–5 KUD+ scale by default.** The spec is explicit about this design choice: *"For most purposes of alignment, the achievement level of a skill is binary, rather than on a sliding scale. That means there is a threshold level of attainment that is required in order to award a credential that recognizes that skill ... [the spec covers] cases for alignment of skills that indicate an achievement level of the skill that the credential recognizes"* (`index.html`, "Alignment and Achievement Level" section). CTDL-ASN does separately define a `complexityLevel` property on competencies (confirmed to exist at `https://purl.org/ctdlasn/terms/complexityLevel` per search-indexed Credential Engine Registry term page) and a `case:educationLevel` field is carried through in RSD's CASE-LD recipe, but neither is a required, multi-point depth rubric like K/U/D 0–5 — it is optional, coarse, and framework-dependent. **This is a genuine data-model gap relative to our depth-scale model**, not something RSD/CTDL-ASN already solves.
- **Second serialization recipe:** the RSD spec also defines a **CASE-LD** binding (tabs in the spec for "CTDL-ASN/CTDL" vs. "CASE-LD" recipes), reusing `case:associationSet`/`case:CFDocumentURI`/`case:educationLevel` properties. This directly intersects with our existing CASE-export decision: an RSD published via the CASE-LD recipe is, structurally, a CASE competency, so if/when we ever do the deferred CASE export, an RSD-compatible JSON-LD export is nearly the same artifact with a different `@context` — cheap to add as a sibling format later, not a reason to build it now.
- Identifiers: canonical URL (`@id`) per RSD; no separate CTID-style identifier scheme of its own — it borrows CTDL-ASN/CE identifier conventions when published through Credential Engine's registry.

### Tooling (OSMT)

- OSMT: *"a free, open-source instrument to facilitate the production of Rich Skill Descriptor (RSD) based open skills libraries"* (osmt.io homepage, fetched 2026-10-13) / *"OSMT is written in Kotlin with Spring Boot, and Angular. It uses backend-instances of MySQL, Redis, and Elasticsearch"* (GitHub repo description, fetched via WebFetch 2026-10-13). Apache 2.0, self-hostable, with its own skills-library product (search, publish, batch CSV import) built around RSD JSON.
- WGU's own deployment is the largest known public example: *"Western Governors University: Created 13,000+ RSDs in their Skills Library, publishing nine collections initially with quarterly releases planned"* (Credential Engine resource article, fetched 2026-10-13); a later WGU press search put the library at *"175+ collections ... 15,500+ Rich Skills Descriptors"* with topical collections including one *"for professionals who perform and improve written, oral, visual, and digital communication, which includes Marketing Specialists and Communications Specialists"* (WGU Skills Library marketing copy, via search snippet — **[UNVERIFIED]**, not fetched from the primary WGU page directly, and I found no collection specific to printing, prepress, packaging, or graphic communications production in what I could see). Education Design Lab and Southern New Hampshire University are cited as two other public RSD-collection publishers (same Credential Engine article), again general-education/21st-century-skills focused, not print/GC-specific.
- **No existing RSD/OSMT collection for printing, prepress, packaging, or print production management was found or confirmed.** I could not run a live Credential Finder/Skills Library search inside this session (§0), so absence here is "not found," not "confirmed absent" — **[UNVERIFIED]**, worth a manual check at `https://www.wgu.edu/lp/general/wgu/skills-library.html` or OSMT-hosted libraries if this becomes relevant.

### Who uses it / relationship to other standards

- Adopters found: WGU (origin, largest library), Education Design Lab, Southern New Hampshire University (Credential Engine resource article, fetched 2026-10-13). General-education and broad employability-skills focus predominates in what's publicly described; no sector-specific (print/graphic communications) adopter surfaced.
- Relationship to CASE: RSD offers a CASE-LD serialization recipe directly (see above) — RSD and CASE are not competitors here, RSD treats CASE as one of two supported wire formats.
- Relationship to ESCO/O*NET: via the `occupations`/`ceterms:occupationType` property, aligned to "BLS SOC or O*NET" codes (spec quote above); no direct ESCO property in RSD itself, but since RSD rides on CTDL-ASN, it inherits whatever ESCO/O*NET crosswalk Credential Engine maintains at the CTDL layer (see §2).
- Relationship to CLR/LER: not found as a direct RSD feature; this connection runs through CTDL (§2), since RSD passes through to CTDL-ASN for any CLR/LER interoperability.

### Relationship to CLR/LER and CASE

- CLR/LER compatibility: *"The Credential Engine Registry supports the housing of competencies associated with credentials offered by institutions. ## 3. Assessment — fit for this tool

**(a) Adopt either as our internal model? No, for both.** Our KUD+ model (three dimensions, 0–5 depth scale, evidence-above-zero rule, dissociation cases) is deliberately richer on the *proficiency/depth* axis than anything RSD or CTDL-ASN natively requires. RSD's own spec explicitly treats skill attainment as binary-by-default ("threshold level of attainment," not a sliding scale — §1), and CTDL-ASN's `complexityLevel` is a single optional field, not a required 3×6-point rubric. Rebuilding our internal model on either standard would be a strict downgrade in expressiveness for the thing this tool is actually for (Q1/Q2 depth-based curriculum mapping). This mirrors the CASE decision already on record.

**(b) Cheap compatibility choices now?** One is genuinely cheap and worth doing opportunistically, not urgently: when we assign O*NET 31.0 element/task IDs to bundles (current work), **also store the O*NET SOC/element code verbatim** (we likely already do, since that's the join key) — this is the one field RSD/CTDL-ASN would need from us for a future crosswalk (`occupations`/`ceterms:occupationType`), and it costs nothing extra since it's already our primary key into O*NET. No other CTDL-ASN/RSD field is worth adding speculatively now (e.g., don't add a `complexityLevel` column — our depth scale already covers that ground and better).

**(c) Export/publish later — what's the trigger?** Don't build either export speculatively. Plausible triggers, any one of which would justify picking this back up:
  - A specific employer, state workforce agency, or accreditor in the P3 phase asks for machine-readable competency data in CTDL-ASN or RSD JSON-LD specifically (as opposed to CASE, which we already cover as deferred).
  - Clemson or SC's system office adopts the Credential Registry as a state reporting mechanism (not currently observed — see Clemson search caveat in §2; worth a one-time manual check at `credentialfinder.org` before P3 kicks off, since I could not verify this from here).
  - We want our competency catalog to be independently discoverable/linkable from the broader skills ecosystem (SEO/visibility play) — low priority, not requested.
  - If/when the deferred CASE export is actually built, add a CTDL-ASN/RSD JSON-LD sibling export at the same time — the mapping work (competency text, category, alignment types, O*NET occupation codes) overlaps almost entirely with what a CASE export needs, per §1/§2's CASE-LD/CTDL-ASN dual-recipe structure. This is the single most concrete, low-cost opportunity identified in this review.

**(d) Existing RSD/CTDL-ASN collections as an additional link vocabulary alongside O*NET/ESCO?** Not found. The only concretely identified RSD libraries (WGU's 175+ collections, Education Design Lab, SNHU) are general-education / cross-cutting employability-skills focused; none surfaced for printing, prepress, packaging, print production management, or GC-specific marketing/sales (§1). **This was not exhaustively verified** — the Credential Finder/Skills Library couldn't be searched live from this session (§0) — so treat "none found" as "none found in a search-engine-mediated pass," and do a direct manual search before concluding definitively there's nothing usable. On current evidence, O*NET (already in progress) and ESCO (already named in the plan) remain the right primary link vocabularies; RSD/CTDL-ASN would mostly just be O*NET's data *repackaged*, not new coverage, for our specific sector.

**(e) Relevance to P3 employer-side requirements (position capture, per-career weights/depths).** Low-to-moderate. CTDL-ASN's `ceasn:Competency`↔`ceterms:Job`/`ceterms:Occupation`/`ceterms:WorkRole` relations (via `competencyCategory`'s domain, §2) are conceptually close to what P3 needs (linking competencies to occupations/roles), and the O*NET-native alignment already in the Credential Registry (DOL publishes O*NET as CTDL-ASN linked data, §2) could, in principle, be a secondary cross-check source for which competencies the DOL itself associates with print/graphic-communications-adjacent SOC codes — worth a look only if our own employer-interview data (Position Capture) turns out thin for a given occupation and we want an external sanity check. It should not be treated as a required input.
